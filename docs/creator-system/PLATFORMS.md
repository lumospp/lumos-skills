# Platforms — 平台是不同表达界面，不是多套创作系统

## 1. 总原则

Creator System 先形成一个 **canonical draft / 核心判断**，再决定最自然的平台。

```text
一个 Seed / 问题
  ↓
一个母稿 / 一个核心判断
  ↓
一个主平台发布
  ↓
如果成本很低，再适配第二个平台
```

前 10 次创作：**一次只要求 1 个主平台，最多 1 个副平台。**

不要把“全平台运营”当成当前目标。

---

## 2. 各平台在系统里的角色

### 小红书 — 问题入口 / 认知冲突测试

适合：

- 具体日常困惑；
- “明明 X，却 Y”的反常现象；
- 一个核心判断可以拆成少量信息块；
- 希望快速获得评论、私信和真实 Case。

不要：

- 把 3000 字文章硬拆成 12 张图；
- 每页塞满字；
- 为了冲突感制造不存在的经历或共识。

一个常用结构：

```text
封面：具体冲突
↓
真实场景
↓
通常解释
↓
更好的机制 / 判断
↓
边界 / 反例
↓
一个可带走的行动或问题
```

---

### 视频号 — 口头思考 / 信任建立

适合：

- 一个观点可以用嘴讲清；
- 有现实故事或案例；
- 语气和人格本身有助于理解。

推荐：

```text
前 5~10 秒：直接说冲突
中间：只走一条逻辑线
结尾：留下一个新判断 / 行动
```

不要把文章逐字朗读。

如果自己无法不看稿讲出主线，也可以把它当成“是否真正内化”的测试信号，而不是硬性门槛。

---

### 公众号 — Canonical Essay / 长期知识资产

适合：

- 一个问题值得完整论证；
- 有证据、竞争解释和边界；
- 三个月以后仍值得读。

公众号可以承担：

> **当前这个问题最完整、最可辩护的公开版本。**

不要因为“公众号应该长”而拉长。

---

### X / 微博 — 观点原子 / 问题探针

适合：

- 100~500 字 Insight Atom；
- 一个尚未成熟的问题；
- 一个局部反常识；
- 对已有母稿做二次切片。

它可以承担公开 R&D：

```text
想法 → 发出去 → 看反驳 / 共鸣 → 更新 → 再长成文章
```

不要变成必须每日打卡的 KPI。

---

### 知乎 — 真实问题库 / 长答案验证场

优先作为：

- 发现真实问题；
- 观察大众已有解释；
- 在高度匹配的问题下发布已有母稿的回答版本。

不要为了知乎单独建立另一套研究流程。

---

### GitHub — 方法与可复用资产

GitHub 不承担日常内容发布。

适合沉淀：

- Creator System；
- Agent Skills；
- Prompt；
- 公开模板；
- 可复用方法；
- 经过真实使用的工具和 Case。

---

## 3. 平台选择规则

母稿完成后只先问：

> **这个问题最自然的表达媒介是什么？**

- 需要完整论证 → 公众号；
- 需要快速测试冲突 / 找真人问题 → 小红书；
- 需要口头故事和人物语气 → 视频号；
- 只有一个观点原子 → X / 微博；
- 已有高度匹配提问 → 知乎。

流量是二级变量，表达匹配和真实反馈优先。

---

## 4. V0.3 周末建议

本周末不要先规划内容矩阵。

选出一个真实 Seed / Question 后：

```text
想快速验证观点 / 找 Case
→ 小红书

想完整形成一篇自己认可的认知资产
→ 公众号
```

如果发布主平台以后，第二平台适配几乎不增加负担，再顺手做；否则不做。

**真正目标是跑通一次“思考 → 发布 → 现实反馈”，不是证明自己能同时运营多个平台。**
