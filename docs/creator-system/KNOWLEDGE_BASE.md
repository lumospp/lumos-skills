# Knowledge Base — 如何整理而不把自己整理死

## 1. 原则

知识库的第一目标不是“整齐”，而是：

> **以后能找回问题、证据、判断和反馈之间的关系。**

不要按平台建知识库：

```text
公众号/
小红书/
视频号/
```

这样会让同一个问题被拆成三个孤岛。

应该以“问题”为主对象。

---

## 2. 推荐目录（本地 Markdown / Obsidian / Git 都可）

```text
creator/
├── 00-inbox/                  # 快速捕捉，允许很乱
├── 10-problems/               # 问题卡：系统核心
├── 20-research/               # 研究与证据
├── 30-insights/               # 已形成但未必发布的观点原子
├── 40-drafts/                 # 母稿
├── 50-published/              # 已发布索引，不复制平台全文也可
├── 60-feedback/               # 评论/数据/复盘
├── 70-models/                 # 模型卡：ICAP、Knight 等
├── 80-projects/               # 与产品/实验直接相关的问题
└── templates/
```

V0.1 如果嫌目录多，可以只先建：

```text
inbox/
problems/
drafts/
feedback/
```

其他目录在真实需要出现后再建。

---

## 3. 核心对象不是“文章”，是 Problem ID

每个值得研究的问题分配一个简单 ID：

```text
P-2026-0902-01
```

例如：

```markdown
# P-2026-0902-01 AI 讲清楚了为什么我还是没学会

status: researching
tags: [AI, learning]
source: self
created: 2026-09-02

## 现象
AI 解释时感觉很懂，关闭后不能复述。

## 真问题
AI 降低理解难度时，什么时候会促进学习，什么时候会制造“学会了”的错觉？

## 当前判断
...

## 相关研究
- R-...

## 产出
- 小红书：...
- 公众号：...

## 反馈
- F-...
```

所有研究、草稿、反馈都通过 Problem ID 关联，而不是依赖文件夹记忆。

## 4. Model Card — 模型库只做“解释工具箱”

模型库不是文章选题库。

每个模型只保存这些：

```markdown
# 奈特不确定性

## 一句话
无法可靠给出概率分布的不确定性。

## 它最适合解释
- 新市场/新产品
- 创业判断
- 某些职业与组织问题

## 它不能直接解释
- 所有风险
- 所有高薪现象

## 常见误用
- 把 unknown unknowns 全部等同于 Knightian uncertainty
- 把“有不确定性”当成万能解释

## 我真实用它解释过的问题
- P-...
```

只有一个模型真实解释过多个问题以后，它才逐渐变成自己的工具。

---

## 5. Source / Evidence 不要收藏一切

避免把知识库变成第二个浏览器收藏夹。

只保存：

- 真正承担核心 Claim 的证据；
- 特别好的反例；
- 以后可能重复使用的综述/原始来源；
- 自己写下来的解释和判断。

链接本身不是知识。

最小记录：

```text
来源：
它支持什么：
它不支持什么：
我为什么以后还需要它：
```

如果这四行都写不出来，不必收藏。

---

## 6. 内容母稿与平台稿的关系

推荐：

```text
P-xxx
  ├─ canonical.md      # 核心母稿 / 当前最完整理解
  ├─ xhs.md            # 可选
  ├─ video.md          # 可选
  └─ feedback.md
```

平台稿是母稿的不同表达，不是新的知识节点。

母稿更新时，不要求历史已发布内容同步修改；现实发布本身就是时间切片。

---

## 7. Git 与 Obsidian 的分工建议

### 本地 Obsidian / Markdown

适合：

- 私人问题；
- 未成熟判断；
- 日常 inbox；
- 草稿；
- 个人项目过程。

### GitHub

适合：

- 已经过验证、值得长期保留的方法；
- Skill / Prompt；
- 可以公开的研究框架；
- 创作系统本身；
- 不涉及隐私的典型 Case。

不要为了“让 AI 读到”就把所有私人知识推到公开仓库。

## 8. V0.1 最省摩擦配置

今晚只需要本地建立：

```text
creator/
├── inbox.md
├── problems/
├── drafts/
└── feedback.md
```

甚至 `inbox.md` 里可以先用一行一个问题：

```text
- [ ] AI 明明讲懂了，为什么关掉它我就不会？
- [ ] 为什么职业规划越详细，我有时越焦虑？
- [ ] 为什么 AI 写代码越快，review 越慢？
```

系统服务创作，不要让整理成为新的拖延方式。
