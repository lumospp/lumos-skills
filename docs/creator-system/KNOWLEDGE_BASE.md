# Knowledge Base — 如何整理而不把自己整理死

## 1. 原则

知识库第一目标不是整齐，而是：

> **以后能找回 Seed、问题、证据、思维路线、判断和反馈之间的关系。**

不要按平台建知识库，也不要把知识库变成思维模型收藏馆。

现在区分两个核心对象：

1. **Seed**：尚未长成问题的想法、概念、连接、原话；
2. **Problem**：经过结晶后，值得研究、判断或公开表达的问题。

Seed 可以很松散；Problem 才需要 Problem ID。

---

## 2. 推荐目录

```text
creator/
├── 00-inbox/                  # Seed / 快速捕捉，允许很乱
├── 10-problems/               # 已结晶的问题卡
├── 20-research/               # 研究与证据
├── 30-insights/               # 观点原子
├── 40-drafts/                 # 母稿
├── 50-published/              # 已发布索引
├── 60-feedback/               # 评论 / 数据 / 复盘
├── 70-models/                 # 课程模型 + 自己的真实理解
├── 80-projects/               # 产品 / 实验相关问题
└── templates/
```

最省摩擦配置仍然可以只是：

```text
inbox.md
problems/
drafts/
feedback.md
```

---

## 3. Seed Pool — 不要过早建 Problem ID

Seed 可以只是一行：

```text
- 今天学到奈特不确定性，感觉它和“总想等确定了再行动”有点关系。
- 刚跟同事聊到：AI 写代码越快，review 好像越慢。
- 有个感觉：人可能并不是讨厌工作，而是讨厌没有选择的工作。
```

甚至可以只是原话 + 日期。

Seed 经过对话孵化后，如果出现了明确张力、候选判断或值得研究的问题，再升级：

```text
Seed
 ↓
Incubate / Crystallize
 ↓
Problem ID
```

不要求每个 Seed 升级。很多 Seed 最后只是一个连接、一条私人笔记或一个未来触发器。

---

## 4. Problem ID — 已结晶问题才建立

格式：

```text
P-2026-0902-01
```

例如：

```markdown
# P-2026-0902-01 AI 讲清楚了为什么我还是没学会

status: researching
source: seed / self / user / comment / platform / work / conversation
created: 2026-09-02

## 来源 Seed
原始那句话 / 链接：

## 真问题
AI 降低理解难度时，什么时候会促进学习，什么时候会制造“学会了”的错觉？

## 对话结晶
我真正关心的是：
出现的核心张力：
AI 提出的但我尚未确认：

## Thinking Route
主工具：
为什么：
补充 / 反证工具：

## Key Unknown
最可能改变当前判断的未知：

## 当前判断
...

## 关键依据
...

## 边界 / 最强反例
...

## Update Condition
什么证据出现时应修正或推翻：

## 相关研究
- R-...

## 产出
- canonical：...
- 小红书：...

## 反馈
- F-...
```

`Thinking Route` 只在模型确实改变判断时记录，不要求填满。

## 5. 对话本身也是材料，但不要永久保存一切

如果一个 Seed 是通过与 AI / 人的长对话逐渐成形，不需要把整段聊天永久搬进知识库。

结晶后只保存高价值部分：

```text
用户自己的关键原话：
重要纠正 / 转折：
真实 Case：
最后形成的张力：
候选判断如何变化：
仍未解决：
```

原始对话只有在以后确实可能需要追溯时才保存链接或完整记录。

知识库保存的是**认知演化的关节点**，不是聊天日志仓库。

## 6. Model Card — 会成长的解释工具箱

模型库不是文章选题库，也不是课程笔记仓库。

课程 / Skill 的定义、机制、调用信号和边界，是经过筛选的重要起点；目标是通过真实 Case 逐步内化。

### Source Layer

忠实保留来源：

```markdown
# 模型名

## 来源定义
## 来源调用信号
## 来源核心机制
## 来源边界
```

### Personal Layer

```markdown
## 我现在怎么理解它

## 我的真实触发信号

## 它最适合改变什么
问题表示 / 判断标准 / 机制 / 行动 / 风险边界

## 它不能直接解释什么

## 我最容易怎么误用

## 最强竞争 / 反证工具

## 我真实用过的 Problem ID
- P-...

## 它怎样改变过我的判断
- P-...：原判断 → 新判断

## 新 Case 带来的修正
- 日期 / Problem ID：
```

原则：

> **Source Layer 保真，Personal Layer 生长。**

只有真实使用过、真正改变过判断的模型，才值得逐渐补强个人层。

## 7. Modern Thinking Skill 与 Model Library

Modern Thinking Skill 是默认 Router / Reasoning Engine：

- 自动选主工具；
- 找补充 / 反证工具；
- 让用户不必先知道模型名；
- 把模型落到机制、行动和更新条件。

Model Library 负责：

- 保存来源；
- 保存自己的真实使用记录；
- 保存触发器、边界、误用和竞争工具；
- 让高频模型逐渐从“AI 提醒”变成“自己会想到”。

长期：

```text
AI 路由
 ↓
真实 Case 使用
 ↓
个人触发器 / 边界 / 案例
 ↓
自己 pass@1 调用
 ↓
AI 更多做陌生工具搜索和反证
```

---

## 8. Source / Evidence 不要收藏一切

只保存：

- 真正承担核心 Claim 的证据；
- 特别好的反例；
- 以后可能重复使用的综述 / 原始来源；
- 自己形成的解释和判断。

最小记录：

```text
来源：
它支持什么：
它不支持什么：
我为什么以后还需要它：
```

链接本身不是知识；模型名本身也不是知识。

---

## 9. 母稿与平台稿

```text
P-xxx
  ├─ canonical.md
  ├─ xhs.md          # 可选
  ├─ video.md        # 可选
  └─ feedback.md
```

平台稿是母稿不同表达，不是新知识节点。

如果文章是从长对话里长出来的，`canonical.md` 可以保留少量“思路演化”痕迹，但不需要复制全部聊天。

---

## 10. Git 与 Obsidian 分工

### Obsidian / 本地 Markdown

适合：

- Seed Pool；
- 私人问题；
- 未成熟判断；
- 对话结晶；
- 草稿；
- 个人项目；
- Model Card Personal Layer。

### GitHub

适合：

- 已验证的方法；
- Skill / Prompt；
- 创作系统；
- 可公开研究框架；
- 不涉及隐私的典型 Case；
- 比较稳定、对别人也有价值的模型使用经验。

不要为了让 AI 读到就把所有私人材料公开。

---

## 11. 最省摩擦配置

`inbox.md` 允许混合 Seed 和已经较清楚的问题：

```text
- [seed] 今天学到“托付”，感觉它可能和高薪的本质有关。
- [seed] 跟同事聊到 AI 写代码快但 review 慢。
- [problem] AI 明明讲懂了，为什么关掉它我就不会？
```

只有真正结晶后才搬进 `problems/`。

系统服务创作和认知成长，不要让整理成为新的拖延方式。
