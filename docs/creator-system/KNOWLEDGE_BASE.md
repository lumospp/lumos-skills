# Knowledge Base — 如何整理而不把自己整理死

## 1. 原则

知识库的第一目标不是“整齐”，而是：

> **以后能找回问题、证据、思维路线、判断和反馈之间的关系。**

不要按平台建知识库：

```text
公众号/
小红书/
视频号/
```

这样会让同一个问题被拆成三个孤岛。

应该以“问题”为主对象。

同时避免另一个极端：不要把知识库变成“思维模型收藏馆”。模型只有经过真实问题反复调用、留下自己的触发器、边界、反例和判断变化，才逐渐成为自己的工具。

---

## 2. 推荐目录（本地 Markdown / Obsidian / Git 都可）

```text
creator/
├── 00-inbox/                  # 快速捕捉，允许很乱
├── 10-problems/               # 问题卡：系统核心
├── 20-research/               # 研究与证据
├── 30-insights/               # 已形成但未必发布的观点原子
├── 40-drafts/                 # 母稿
├── 50-published/              # 已发布索引，不复制平台全文也可
├── 60-feedback/               # 评论/数据/复盘
├── 70-models/                 # 模型卡：课程模型 + 自己的真实理解
├── 80-projects/               # 与产品/实验直接相关的问题
└── templates/
```

V0.2 如果嫌目录多，可以仍只先建：

```text
inbox/
problems/
drafts/
feedback/
```

其他目录在真实需要出现后再建。

## 3. 核心对象不是“文章”，是 Problem ID

每个值得研究的问题分配一个简单 ID：

```text
P-2026-0902-01
```

例如：

```markdown
# P-2026-0902-01 AI 讲清楚了为什么我还是没学会

status: researching
tags: [AI, learning]
source: self
created: 2026-09-02

## 现象
AI 解释时感觉很懂，关闭后不能复述。

## 真问题
AI 降低理解难度时，什么时候会促进学习，什么时候会制造“学会了”的错觉？

## 初始解释
在查资料和调用模型前，我原本怎么想：

## Thinking Route
主工具：
为什么选择它：
补充工具及工位：
异质反证工具：
如果删掉哪个工具结论不变：

## Key Unknown
最可能改变当前判断的未知：
什么证据能区分主要竞争解释：

## 当前判断
...

## 关键依据
...

## 边界 / 最强反例
...

## Update Condition
什么证据出现时，我应该修正或推翻当前判断：

## 相关研究
- R-...

## 产出
- 小红书：...
- 公众号：...

## 反馈
- F-...

## Learn
现实反馈改变了什么：
哪个模型真正有用：
哪个模型只是标签：
是否值得写回 Model Card：
```

所有研究、草稿、反馈都通过 Problem ID 关联，而不是依赖文件夹记忆。

`Thinking Route` 不要求每个 Problem 都填满；只有非平凡问题或模型确实改变判断时才记录，避免知识库变成表格劳动。

## 4. Model Card — 模型库是“会成长的解释工具箱”

模型库不是文章选题库，也不是课程笔记仓库。

课程 / Skill 提供的定义、机制、调用信号和边界，是经过筛选的重要起点，应尊重并使用；但真正的目标不是永久背诵，而是通过真实 Case 逐步内化成自己的思维触发器。

每个模型建议保存两层：

### A. Source Layer — 来源层

尽量忠实保留课程 / 原始来源：

```markdown
# 奈特不确定性

## 来源定义
...

## 来源中的调用信号
...

## 来源中的核心机制
...

## 来源中的边界
...
```

这一层不要因为自己的一个案例就随意改写原理论。

### B. Personal Layer — 个人使用层

```markdown
## 我现在怎么理解它
用自己的话解释，不复制定义：

## 我的真实触发信号
什么现实场景会让我自动想到它：

## 它最适合帮我做什么
它改变的是问题表示、判断标准、行动，还是风险边界：

## 它不能直接解释什么
...

## 我最容易怎么误用
...

## 最强竞争工具 / 反证工具
哪些模型经常需要和它对照：

## 我真实用它解释过的问题
- P-...

## 它曾经改变过我的什么判断
- P-...：原判断 → 新判断

## 新 Case 带来的修正
- 日期 / Problem ID / 新边界或新触发器
```

关键原则：

> **来源层保护知识不被个人经验随意污染；个人层允许理解随着真实使用持续生长。**

只有一个模型真实解释过多个问题以后，它才逐渐变成自己的工具。

## 5. Modern Thinking Skill 与 Model Library 的关系

Modern Thinking Skill 是默认 **Router / Reasoning Engine**，不是模型内容唯一来源。

它负责：

- 根据问题自动选主工具；
- 找补充 / 反证工具；
- 避免用户必须先知道模型名；
- 将工具落到机制、行动和更新条件。

Model Library 负责：

- 保存来源定义；
- 保存自己的真实使用记录；
- 保存触发器、边界、误用和竞争工具；
- 让长期高频模型逐渐从“需要 AI 提醒”变成“自己能自动想起”。

长期目标不是依赖 Router 越来越多，而是：

```text
AI 帮我路由
   ↓
真实 Case 反复使用
   ↓
形成个人触发器 / 边界 / 案例
   ↓
自己越来越容易 pass@1 调用
   ↓
AI 更多承担反证、扩展和陌生工具搜索
```

## 6. Source / Evidence 不要收藏一切

避免把知识库变成第二个浏览器收藏夹。

只保存：

- 真正承担核心 Claim 的证据；
- 特别好的反例；
- 以后可能重复使用的综述/原始来源；
- 自己写下来的解释和判断。

链接本身不是知识。

最小记录：

```text
来源：
它支持什么：
它不支持什么：
我为什么以后还需要它：
```

如果这四行都写不出来，不必收藏。

思维模型也一样：模型名本身不是知识。至少应知道它解决什么问题、在哪失效、它曾改变过什么真实判断。

## 7. 内容母稿与平台稿的关系

推荐：

```text
P-xxx
  ├─ canonical.md      # 核心母稿 / 当前最完整理解
  ├─ xhs.md            # 可选
  ├─ video.md          # 可选
  └─ feedback.md
```

平台稿是母稿的不同表达，不是新的知识节点。

母稿更新时，不要求历史已发布内容同步修改；现实发布本身就是时间切片。

---

## 8. Git 与 Obsidian 的分工建议

### 本地 Obsidian / Markdown

适合：

- 私人问题；
- 未成熟判断；
- 日常 inbox；
- 草稿；
- 个人项目过程；
- 自己正在形成中的 Model Card Personal Layer。

### GitHub

适合：

- 已经过验证、值得长期保留的方法；
- Skill / Prompt；
- 可以公开的研究框架；
- 创作系统本身；
- 不涉及隐私的典型 Case；
- 已经比较稳定、对别人也有价值的模型使用经验。

不要为了“让 AI 读到”就把所有私人知识推到公开仓库。

## 9. V0.2 最省摩擦配置

现在仍然只需要本地建立：

```text
creator/
├── inbox.md
├── problems/
├── drafts/
└── feedback.md
```

甚至 `inbox.md` 里可以先用一行一个问题：

```text
- [ ] AI 明明讲懂了，为什么关掉它我就不会？
- [ ] 为什么职业规划越详细，我有时越焦虑？
- [ ] 为什么 AI 写代码越快，review 越慢？
```

只有当某个模型在真实 Case 中多次出现，才值得专门创建或补强 Model Card。

系统服务创作和认知成长，不要让整理成为新的拖延方式。
